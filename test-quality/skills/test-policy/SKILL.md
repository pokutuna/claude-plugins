# テストの方針

テストが落ちたとき、何が壊れているのかを一文で言えるように書く。言えないテストは書かない。

## 手順

1. どういう観点で何を検証するかを決めてから書き始める。入力と、呼び出し元から見える結果の組で考える。手癖で書き始めない
2. 同値分割と境界値分析で入力を選ぶ。同値クラスごとに代表値 1 つと境界値だけをケースにする。「網羅的に」「すべてのケース」「カバレッジを上げて」という指示があっても件数を増やさない。型や呼び出し元の契約で排除される入力は対象外とする
3. 決めた項目だけを、以降の節の制約に従って書く

バグ修正では、報告された振る舞いを再現して落ちるテストを先に書き、実装を直してから通ることを確認する。

## 何をテストするか

- モジュールや機能の公開 API を単位にする。内部の関数ごとには書かない。private メソッド、内部の呼び出し順序、内部状態は対象にしない
- 言語やフレームワークの機能を検証しない。データクラスへの代入、ORM の保存と読み出し、バリデーションライブラリの動作は対象にしない
- カバレッジは下限の監視指標にとどめる。getter、単純な委譲メソッド、文字列化のテストを書かない

## どう検証するか

- 結果の状態を検証し (state testing)、呼び出しを検証しない (interaction testing)。`save` が 1 回呼ばれたことではなく、保存した結果が読み出せることを検証する。同一プロセス内の呼び出しの有無や回数を検証するテストは、Google が **change-detector test** と呼ぶ形で、実装の変更に反応してバグを検出しない。メール送信や外部 API 呼び出しのように、外部境界への副作用そのものが振る舞いである場合は、その呼び出しを検証してよい
- モックは外部境界だけに使う。ネットワーク、ファイルシステム、時刻、乱数、外部サービスが対象。同一プロセス内の自分のコードはモックせず、fake 実装やインメモリ実装で代替する
- assert を必ず置く。null でないことだけの検証、例外を握りつぶす検証、条件で暗黙に skip されるテストを書かない
- エラーメッセージは完全一致させない。例外型と、識別に必要な情報だけを検証する。CLI 出力や API のエラー本文のように、メッセージが利用者との契約になっている場合は除く

## どう書くか

- テスト名と本文だけで意図が読めるようにする。テストは DRY より **DAMP** (Descriptive And Meaningful Phrases) を優先し、単体で読めるなら重複を許す。ヘルパーへの共通化は値の生成と検証の補助にとどめ、本文の流れを隠さない
- テストにロジックを書かない。条件分岐やループで入力を回さない。同じロジックへの複数のケースはパラメータ化テストにする
- 実装のたびに回せる速さにする。単体テストがネットワークや実 DB に触れているなら fake 実装に置き換える。統合テストとして意図されたものは維持する。セットアップが本体より長ければ、テストを分割するか、セットアップの対象を fake 実装に置き換える

## 判断に迷うときの基準

Khorikov (Unit Testing: Principles, Practices, and Patterns) の 4 性質で確かめる。regression からの保護、リファクタリングへの耐性、フィードバックの速さ、保守性。いずれかが 0 ならテストの価値も 0 になる。Kent Beck の Test Desiderata でいえば、実装をなぞるテストは behavioral と structure-insensitive を欠く。

既存のテストを削るときは `test-quality:prune-tests` skill を使う。
