# テストの方針

テストが落ちたとき、何が壊れているのかを一文で言えるように書く。言えないテストは書かない。

コーディングエージェントは実装を参照しながらテストを書くため、実装の内部構造を固定するテスト、常に通るテスト、網羅のためのテストを量産しやすい。この skill は、その傾向に対する制約と判断基準をテストを書く時点で与えるためのものである。

## 書く前に決めること

1. **検証項目を先に列挙する**。テストコードを書く前に、検証する振る舞いを一覧にして示す。実装より前に削るのが最も安価で、依頼者がレビューできる形になる
2. **各項目に「落ちたとき何が壊れているか」を付ける**。付けられない項目は落とす
3. **網羅を目標にしない**。「網羅的に」「すべてのケース」という指示があっても、同値クラスごとに 1 つと境界値だけを選ぶ。型や呼び出し元の契約で排除される入力は「起こりえないため対象外」と明示して除く

## 制約

- **public な振る舞いだけをテストする**。private メソッド、内部の呼び出し順序、内部状態は対象にしない。リファクタリングで壊れるテストはバグを検出しない
- **モックは外部境界だけに使う**。ネットワーク、ファイルシステム、時刻、乱数、外部サービスが対象。同一プロセス内の自分のコードはモックしない。内部の協調役の代替が必要なら fake 実装やインメモリ実装を使う
- **呼び出しの有無や回数を検証しない**。`save` が 1 回呼ばれたことではなく、保存した結果が読み出せることを検証する。Google はこの種のテストを **change-detector test** と呼び、振る舞いが変わっていないのに実装変更で落ちる点を問題にしている
- **言語やフレームワークの機能を検証しない**。データクラスへの代入、ORM の保存と読み出し、バリデーションライブラリの動作は自分のコードではない
- **カバレッジは下限の監視指標にとどめる**。目標値にすると getter、委譲メソッド、`__repr__` のテストが生まれる。カバレッジを増やさないテストは追加しない
- **assert を必ず置く**。`assertIsNotNone` だけ、例外を握りつぶす `try`/`except`、条件で暗黙に skip されるテストは、通っているという誤った安心を与える
- **エラーメッセージは完全一致させない**。例外型と、識別に必要な情報だけを検証する
- **同じロジックへの複数のテスト関数はパラメータ化する**

## 判断の根拠

Khorikov (Unit Testing: Principles, Practices, and Patterns) は良いテストの性質を 4 つ挙げ、いずれかが 0 なら全体の価値も 0 だとする。テストを 1 つ書いたら、次の問いで確かめる。

- **regression からの保護**: このテストが落ちるとき、ユーザーに見える振る舞いのどれが壊れているか言えるか
- **リファクタリングへの耐性**: 振る舞いを変えずに実装を書き換えても通り続けるか。モックの呼び出し検証や内部状態の参照があれば否
- **フィードバックの速さ**: 実装のたびに回せる速さか。ネットワークや実 DB に触れるなら fake に置き換えられないか
- **保守性**: テスト名と本文だけで意図が読めるか。セットアップが本体より長ければ否

実装をなぞるテストはリファクタリングへの耐性が 0 で、残す価値がない。

既存のテストを削るときは `prune-tests` skill を使う。
