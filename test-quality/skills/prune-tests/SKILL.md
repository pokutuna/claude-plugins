# テストの削減

テストが落ちたとき、何が壊れているのかを一文で言えるかで判定する。言えないテストは削除候補として扱う。

## 手順

1. 対象範囲を決める。ディレクトリ、モジュール、または直近の差分で追加されたテスト
2. 削除前にスイートを実行し、通っている状態を記録する
3. 各テストについて、落ちたとき何が壊れているかを言えるか確かめる
4. 言えないものは削除する。言えるものも、集約、修正、提案の類型に当たれば振り分け、残りは残す
5. 削除、集約、修正を適用する。依頼が「判断だけ聞かせて」「消す前に見せて」であれば適用せず、分類と根拠を示して終える
6. スイートを再実行し、全件通ることを確認する
7. 依頼者への報告に、削除、集約、修正、提案、残すの区別と、それぞれの理由を書く。提案には選択肢も添える。件数が多くチャットに収まらないときは `prune-tests-YYYYMMDD.md` のような作業ファイルに書く

対象が大きいときは、後述の機械的検出で候補を絞ってから 3 に進む。1 つのテストの要否を問われたときは、変更せず、何が壊れるかと該当する類型だけを答える。

## 削除候補の類型

判定の基準は `test-quality:test-policy` skill の制約に置く。制約に反するテストを、次の 4 つに振り分ける。判定に実装の知識だけで足りるものは独断で適用し、仕様や呼び出し元の契約の知識が要るものは提案にとどめる。

### 削除する

- **実装の写経**: 同一プロセス内の呼び出しの有無や順序をモックで検証している (**change-detector test**)。メール送信や外部 API 呼び出しのように、外部境界への副作用そのものが振る舞いである場合は残す
- **言語やフレームワークの機能の検証**: データクラスへの代入、ORM の保存と読み出し、バリデーションライブラリの動作
- **カバレッジ埋め**: getter/setter、単純な委譲メソッド、文字列化が対象
- **常に通るもの**: assert がない、null でないことだけを見ている、例外を握りつぶしている、条件分岐で暗黙に skip される

```python
# 削除: save が呼ばれたことしか検証していない
def test_create_user_calls_save(mock_repo):
    UserService(mock_repo).create_user("alice")
    mock_repo.save.assert_called_once()

# 残す: 保存された結果を検証している
def test_create_user_persists_user(in_memory_repo):
    UserService(in_memory_repo).create_user("alice")
    assert in_memory_repo.get("alice").name == "alice"
```

### 集約する

検証の意図は妥当だが、同じ情報を複数のテストで繰り返しているもの。依頼者に諮らず適用してよい。

- **同値クラスの重複**。実装が同じ経路で処理する入力の集合を **同値クラス** と呼ぶ。同じ同値クラスの入力を別々のテストで検証しても、得られる情報は 1 つ分しかない。代表値 1 つと境界値を残してパラメータ化テストにまとめる。同値クラスの区切りが実装から読めない場合は提案に回す

```python
# 仕様: 10 個以上の購入で 5% 割引

# 集約前: 1, 2, 3 はどれも「10 個未満」の同じ経路を通り、同じ事実しか検証しない
def test_discount_qty_1(): assert discount(1) == 0
def test_discount_qty_2(): assert discount(2) == 0
def test_discount_qty_3(): assert discount(3) == 0

# 集約後: 各同値クラスの代表値と境界値だけを残す
@pytest.mark.parametrize("qty, expected", [(0, 0), (1, 0), (9, 0), (10, 5)])
def test_discount(qty, expected): assert discount(qty) == expected
```

### 修正する

検証の意図は妥当だが書き方に問題があるもの。`test-quality:test-policy` の「どう検証するか」「どう書くか」に合わせて書き換える。

- **エラーメッセージの完全一致**。例外型と識別に必要な情報だけの検証に置き換える。CLI 出力や API のエラー本文のように、メッセージが利用者との契約になっている場合は残す
- **内部コードのモック**。fake 実装やインメモリ実装に置き換える
- **flaky なテスト**。原因を特定して直す。直せなければ変更せず提案に回す。放置すると落ちても無視されるようになり、スイート全体の信頼を損なう

### 提案にとどめる

削除候補として理由と選択肢を示し、依頼者の判断を仰ぐ。テストファイルには手を入れない。

- **起こりえない異常系**。型システムで排除されている値を渡す、呼び出し元との契約上ありえない入力を渡す。契約が明文化されていない場合、その入力が本当に起こりえないかは依頼者しか判断できない
- **別の層で保証済み**。集約の振る舞いをテストしたうえで、その内部の依存先にも同じ観点のテストがある。上位で保証している結果を再検証しているものが対象で、依存先に独自のテストがあること自体は問題にしない

報告の例: 「`test_parse_negative_qty` は起こりえない異常系の疑い。`qty` は呼び出し元の `OrderForm` で 1 以上に検証済み。フォーム以外から `parse` を呼ぶ経路がなければ削除、あれば残す」

## 機械的に検出する

**1 箇所壊して落ちる数を数える**。判定に迷うテストが対象とする実装の条件や戻り値を 1 箇所だけ手で書き換えてスイートを実行し、落ちたテストを数える。書き換えたら元に戻す。同じ公開 API の同じ観点を検証するテストが複数落ちるなら、同値クラスの重複として集約の候補にする。共通の下位関数を壊して複数の公開 API のテストが落ちるのは正当で、冗長ではない。変更した行がテストでカバーされているのに何も落ちなければ、そのテスト群は常に通る類型に当たる。追加ツールなしで実行でき、標準の手段とする。

**ミューテーションテスト**はこの作業を自動化する。言語ごとにツールがある。実行コストが高いため、依頼者が求めた場合か、対象が大きい場合に限って使う。全ミュータントの撲滅は目標にしない。

**カバレッジの差分**で新しく追加されたテストを見る。追加前後でカバレッジが増えないテストは、既存のテストと重複している疑いがある。候補として手順 3 に回す。Meta の TestGen-LLM が生成テストの採否に使うフィルタと同じ考え方で、直近の差分を対象にするときに使う。

**書きすぎの目安**として、テストコードと実装コードの行数比を見る。比率そのものに閾値はないが、突出したモジュールから調べる。
