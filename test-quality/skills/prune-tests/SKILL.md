# テストの削減

テストが落ちたとき、何が壊れているのかを一文で言えるかで判定する。言えないテストは削除候補として扱う。

明らかに無駄なものは削除し、判断にドメイン知識が要るものは提案にとどめる。削除はテストスイートの実行で前後を確認しながら行う。

## 手順

1. 対象範囲を決める。ディレクトリ、モジュール、または直近の差分で追加されたテスト
2. 削除前にスイートを実行し、通っている状態を記録する
3. 各テストに「落ちたとき何が壊れているか」を一文で付ける。付けられないものを下の類型に当てはめる
4. 類型ごとに、削除、集約、提案のいずれかに振り分ける
5. 削除と集約を適用し、スイートを再実行する
6. 提案にとどめたものは、理由と選択肢を添えて依頼者に示す

対象が大きいときは、後述の機械的検出で候補を絞ってから 3 に進む。

## 削除候補の類型

### 削除するもの

判定に実装の知識だけで足りる類型。

- **実装の写経**。モックを組んで `repo.save` が 1 回呼ばれたこと、特定の順序で呼ばれたことを検証する。振る舞いではなく内部構造を固定しているため、リファクタリングで壊れる一方、バグは検出しない。Google の用語では change-detector test
- **言語やフレームワークの機能の検証**。データクラスへの代入、ORM の保存と読み出し、バリデーションライブラリの動作。自分が書いたコードを検証していない
- **カバレッジ埋め**。getter/setter、単純な委譲メソッド、`__repr__` を対象にしたテスト
- **常に通るもの**。assert がない、`assertIsNotNone` だけ、`try`/`except` で例外を握りつぶしている、条件分岐で暗黙に skip される。通っているという誤った安心を与えるため、無駄であるより有害である

### 提案にとどめるもの

判定に仕様や呼び出し元の契約の知識が要る類型。削除候補として理由を示し、依頼者の判断を仰ぐ。

- **起こりえない異常系**。型システムで排除されている `None` を渡す、呼び出し元との契約上ありえない入力を渡す。契約が明文化されていない場合、その入力が本当に起こりえないかは依頼者しか判断できない
- **同値クラスの重複**。`[1, 2, 3]` に対する 3 つのテストは 1 つ分の情報しか持たない。どれを残すかと、境界値の意図があったかを確認する
- **別の層で保証済み**。集約の振る舞いをテストしたうえで、その内部の依存先にも同じ観点のテストがある。上位で保証している結果を再検証しているものが対象で、依存先に独自のテストがあること自体は問題にしない

## 削除せず修正するもの

検証の意図が妥当で表現だけが悪い場合は集約する。

- 同じロジックに対する複数のテスト関数は、パラメータ化テストにまとめる
- エラーメッセージの完全一致は、例外型と識別に必要な情報だけの検証に置き換える
- モックを多用した統合テストは、fake 実装やインメモリ DB に置き換える

## 機械的に検出する

**1 箇所壊して落ちる数を数える**。実装の条件や戻り値を 1 箇所だけ手で書き換えてスイートを実行し、落ちたテストを数える。10 個落ちるなら 9 個は冗長の疑いがある。逆に、変更した行がテストでカバーされているのに何も落ちなければ、そのテスト群は常に通る類型に当たる。追加ツールなしで実行でき、標準の手段とする。

**ミューテーションテスト**は上の作業を自動化する。mutmut / cosmic-ray (Python)、Stryker (JS/TS)、PIT (Java)、cargo-mutants (Rust)。実行コストが高いため、依頼者が求めた場合か、対象が大きい場合に限って使う。全ミュータントの撲滅は目標にしない

**書きすぎの目安**として、テストコードと実装コードの行数比を見る。比率そのものに閾値はないが、エージェントが書いたモジュールで比率が突出していれば、そのモジュールから調べる

新しくテストを書くときの制約は `test-policy` skill にある。

## Examples

### Example 1: モジュールのテストを整理する

**User says:** 「`tests/services/` のテストが多すぎるので整理して」

**Actions:**
1. スイートを実行して通っている状態を記録する
2. 各テストに「落ちたとき何が壊れているか」を付け、類型に分類した一覧を示す
3. 実装の写経、フレームワーク機能の検証、常に通るものを削除し、同じロジックの複数関数をパラメータ化にまとめる
4. 起こりえない異常系と同値クラスの重複は、理由を添えて提案する
5. スイートを再実行し、削除前と同じく通ることを確認する

**削除の例:**

```python
# 削除: save が呼ばれたことしか検証していない
def test_create_user_calls_save(mock_repo):
    service = UserService(mock_repo)
    service.create_user("alice")
    mock_repo.save.assert_called_once()

# 残す: 保存された結果を検証している
def test_create_user_persists_user(in_memory_repo):
    service = UserService(in_memory_repo)
    service.create_user("alice")
    assert in_memory_repo.get("alice").name == "alice"
```

### Example 2: 直近の差分で追加されたテストを見る

**User says:** 「さっき追加したテスト、いらないものがあれば削って」

**Actions:**
1. `git diff` で追加されたテスト関数を列挙する
2. 各テストを類型に当てはめ、削除するものと残すものを示す
3. 実装を 1 箇所壊して落ちる数を数え、同じ箇所で複数落ちるテストを冗長として集約する

### Example 3: 1 つのテストの要否を問われた

**User says:** 「このテストは必要?」

**Actions:**
1. 落ちたとき何が壊れているかを一文で答える
2. 言えなければ該当する類型と、削除か修正かを示す。言えれば残す理由を示す
