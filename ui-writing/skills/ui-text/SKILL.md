# UI テキスト

利用者は UI テキストを読む前に走査し、目に入った語から「ここは何か」「何ができるか」「次に何をするか」を判断する。文言は、その判断に必要な情報を、置かれた場所の役割に合う形で示す。

短くする前に、その情報がその場所に必要かを判断する。どこにも要らない情報は削る。その場所での判断には使わないが、利用者が後で必要とする情報は、説明欄やヘルプに移す。

## 進め方

1. 文字列単位ではなく、画面と操作の流れ全体を読む。前の画面、見出し、周囲のボタンや通知で何がすでに伝わっているかを把握する
2. 各テキストの役割 (見出し、項目名、操作、説明、状態の通知) を判別する
3. 役割に合う文型で書き、同じ役割の並びで形を揃える
4. 用語集と既存の UI に合わせて、用語と表記を揃える
5. 実際の表示幅、長い値、変数を差し込んだ結果で確認する

仕様、事実、法的な意味が変わる修正は、依頼者に確認してから行う。分からない仕様を推測で文言にしない。依頼者に確認できない場合は、元の意味を保つ案を採り、確認が要る点として報告する。実際の表示幅を確かめられない場合も、確かめていないことを報告する。

文言の修正には、既存の要素のテキスト、条件による文言の出し分け、アクセシブルな名前 (`aria-label` など) の変更が含まれる。要素の追加や削除、操作の流れの変更 (ボタンの追加、確認ダイアログの廃止など) は UI の変更として扱い、文言の修正とは分けて提案する。依頼者の了承なしに UI を変更しない。

## 役割と文型

テキストの形は役割で決める。

| 役割 | 文型 | 例 |
|---|---|---|
| 画面タイトル、見出し、項目名、タブ、メニュー | 名詞。対象は「の」でつなぐ | 「通知設定」「権限の追加」 |
| ボタン、操作のリンク | 動詞。サ変動詞は語幹、対象は「を」でつなぐ | 「保存」「取り消す」「権限を追加」 |
| 移動のリンク | 移動先を示す | 「請求書一覧に戻る」 |
| チェックボックス、トグル | オンにしたときの状態を動詞句で | 「メールで通知を受け取る」 |
| 状態ラベル、バッジ | 名詞または短い状態語 | 「下書き」「公開中」「失敗」 |
| 説明文、ダイアログ本文、エラー、通知 | です・ます調の文 | 「変更は翌日から反映されます。」 |

- 「通知を設定できます」のような文を見出しにしない。「通知設定」とする
- サ変動詞は「する」を省く (「追加」「削除」)。和語の動詞は終止形で書く (「戻る」「閉じる」「取り消す」)
- 説明文は体言止めにせず、動詞まで書いて句点を付ける

## 並列する要素を揃える

メニュー、タブ、ボタン群、列見出し、設定項目のように並ぶ要素は、文型、敬語の程度、用語、詳しさを揃える。

- 「名前を変更」「メール設定」「パスワードを変更する」は文型が混在している。メニューなら「名前の変更」「メールの設定」「パスワードの変更」とする
- 一つだけ長く詳しい項目は、他より重要だと読まれる。重要度に差がなければ、詳しさも揃える
- 同じ画面で「〜してください」と「ご〜ください」を混在させない
- 同じ対象を別の語で呼ばない (「削除」と「消去」、「ユーザー」と「メンバー」)

## 説明文を置く場所

説明は、ラベルだけでは利用者が判断できないときに置く。例えば、入力の形式や制約があるとき、選択を後から変えられないとき、画面からは分からない影響 (他のメンバーへの通知、連携先への反映など) があるとき、利用者が知らない用語を使うときである。

- ラベルの言い換えにすぎない説明は削る。「メールアドレス」欄に「メールアドレスを入力してください。」は不要
- 見出しで伝えたことを本文で繰り返さない
- 利用者がすべきことか、判断に必要な事実を書く。システムの仕組みの説明だけで終えない。「データは毎日 0 時に同期されます。」より「変更は翌日から反映されます。」
- 長い説明は要点を先頭に置き、詳細はヘルプへのリンクや折りたたみに移す
- 初回だけ必要な案内を常設しない

## 場面ごとのルール

### 画面タイトル、見出し

- 何の画面かを名詞で具体的に示す。同じ製品に設定画面が複数あるなら「設定」ではなく「通知設定」とする
- 一覧であることが明らかなテーブル見出しや画面タイトルには「一覧」を付けない。機能名と同じになり区別が要るときだけ付ける
- 「〜について」のように情報を足さない語を付けない

### ボタン

- 押した結果を動詞で示す。「OK」「はい」「決定」「実行」のように、何が起きるか分からない語を避ける
- 画面内で対象が明らかなら対象を省く (「プロフィールの変更を保存」→「保存」)。同じ画面に対象が複数あれば付ける
- 「キャンセル」は操作を中止するとき、「閉じる」は表示を閉じるだけのときに使う

### リンク

- 「こちら」「詳細はこちら」のように、リンク文字列だけでは移動先が分からない語を避ける。「料金プランの詳細」のように移動先を書く
- 具体的な場所に戻るときは「に」(「一覧に戻る」)、相対的な位置には「へ」(「前へ」) を使う

### フォーム

- ラベルは常に表示する。プレースホルダーは入力を始めると消え、何の欄か分からなくなるので、ラベルの代わりにしない
- プレースホルダーには入力例だけを書く (「例: yamada@example.com」)。指示や必須条件を書かない
- 形式、文字数、範囲の制約は、入力前に見える位置に書く
- 必須と任意の表記は画面全体で統一する
- 入力エラーは項目名と直し方を書く。「入力値が不正です」より「振込金額は半角数字で入力してください」。上限や下限は値を示す
- 「誤った」「不正な」のように利用者を責める語を使わない

### ダイアログ

- 利用者が判断するための内容を書く。何が起きるか、取り消せるか、どうすればよいかを先に示し、仕組みの説明は補足として後に置く
- タイトルと実行ボタンで同じ操作を示す。タイトルは「{対象}の{操作}」、ボタンは「{操作}」とする (「請求書の削除」と「削除」)
- 選択肢は結果で書き分ける。「はい」「いいえ」ではなく「変更を破棄」「編集を続ける」
- 破壊的な操作は、対象、結果、元に戻せないことを書く。「削除しますか?」より「『10月分の請求書』を削除します。削除すると元に戻せません。」
- 元に戻せる操作に確認ダイアログが出ている場合は、ダイアログをやめて完了通知に「元に戻す」を置く設計を提案する

### エラーメッセージ

- 事象 (何が起きたか)、原因、対処の三つを、利用者の視点で書く
- 表示領域が足りないときは、原因、対処、事象の順に優先して残す。利用者の目的は操作を終えることであり、エラーを解消するには原因と対処が要る
- 「エラーが発生しました」だけで終えない。原因が分からないときも、対処 (時間をおいて再度試す、問い合わせ先) を書く
- エラーコードは先頭に置かず、問い合わせ用の補足として末尾に置く
- 「リクエスト」「サーバー」「バリデーション」のような内部の用語を使わない
- システムが保証できない約束 (「すぐに復旧します」) をしない

### 完了通知、読み込み中、空状態

- 完了通知は、何が完了したかを短く書く (「請求書を送信しました」)。「正常に」「無事に」を付けない。次の操作への案内は、利用者が続けて操作する必要があるときだけ添える
- 読み込み中は実際の処理を示す (「請求書を作成しています」)。時間がかかる処理は目安を示す
- 空状態は、空である理由ごとに書き分け、次の操作を示す
  - まだ作成していない: 何を置く場所かと、作成のボタン
  - 検索や絞り込みで該当がない: 条件の変更や解除
  - 権限がない: 誰に依頼すればよいか

### ツールチップ、アイコン

- アイコンだけのボタンには、操作を示すラベルをツールチップとアクセシブルな名前 (`aria-label` など) に付ける
- 操作に欠かせない情報をツールチップに隠さない
- 文なら一文でも句点を付け、語句だけなら句点を付けない

### 一覧、履歴

- 列見出しは名詞で書き、単位は見出しに入れる (「金額 (円)」)
- 操作履歴は「ユーザーを作成」のように動詞形で揃え、「〜しました」を繰り返さない

## 表示領域に合わせた省略

表示領域は限られるので、画面内の他の要素から分かる情報は、文言から削る。次の順に検討する。

1. 画面タイトル、見出し、周囲の要素ですでに示した対象を削る (「プロフィールの変更を保存」→「保存」)
2. 意味を足さない定型句を削る。「設定を行う」→「設定」、「削除することができます」→「削除できます」
3. セクション見出しと重なる接頭辞を削る。見出し「支払い」の下なら「支払い方法」→「方法」。ただし、項目が見出しから離れて表示される場合 (検索結果、通知、エクスポート) は残す

次の情報は、領域が狭くても削らない。

- 対象が複数ありうる場合の操作対象
- 操作の結果、元に戻せないこと、復旧の手段
- 金額、期限、件数などの数値

文字数の上限を一律に決めて合否を判断しない。実際の表示幅で、折り返しと切り詰め、文字の拡大を確認する。

## 用語と表記

- 同じ対象は製品全体で同じ語で呼ぶ。利用者が知っている語を優先し、内部の呼び名 (テーブル名、開発時のコード名) を出さない
- 長音 (「ユーザー」「サーバー」)、送り仮名 (「支払い」「振込」)、接頭辞 (「お支払い」と「支払い」)、全角と半角の表記を揃える
- 作業を始める前に、対象リポジトリの用語集を探す。`glossary`、`terminology`、`用語集` を含むファイルや、textlint の辞書 (`prh.yml` など) があれば従う
- 用語集がなく表記の揺れが見つかった場合は、既存の UI から用語を抜き出した用語集の作成を提案する。ファイルを作るのは、利用者が了承してから

用語集は次の形式で書く。

```markdown
| 用語 | 使わない表記 | 意味と使う場面 |
|---|---|---|
| 振込 | 振り込み、送金 | 口座へお金を移す操作 |
| メンバー | ユーザー、社員 | ワークスペースに招待された人 |
```

## 変数を含む文言

- 長い値、空の値、0 件、1 件を差し込んで、文として成り立つか確認する
- 文字列を連結して文を組み立てない。語順の違う言語に翻訳できなくなる。文全体を一つの文字列にし、値はプレースホルダーで差し込む。翻訳の仕組みがなければ、テンプレートリテラルのように文全体が一か所に見える形にする
- 件数の助数詞を揃える (「{n} 件」と「{n} 個」を混在させない)

## 英語の UI テキスト

- 役割と文型の規則は日本語と同じ。見出しとラベルは名詞句、ボタンは動詞と目的語にする ("Save changes"、"Delete invoice")
- プロジェクトの規約がなければ sentence case にする
- 英語の UX ライティングの資料には語数の基準 (ボタンは 2〜4 語など) がある。これは英語の文言にだけ使い、日本語の文言の長さは表示幅で判断する

## レビューの出力

指摘は次の項目で示す。

- 場所: ファイルと行、または画面と要素
- 現状: 今の文言
- 問題: どのルールに反し、利用者が何に困るか
- 修正案
- 確認事項: 表示幅、変数、前後の画面、仕様によって修正案が変わる指摘にだけ、何を確かめればよいかを書く

指摘は、利用者への影響が大きい順に並べる。取り返しのつかない誤操作やデータの喪失につながるもの、操作を終えられなくなるもの、迷いや誤解を生むもの、一貫性や冗長さの問題の順である。

UI の変更の提案は、文言の指摘の後に別の節としてまとめる。

修正を依頼された場合は直接直し、判断が分かれるものだけを報告する。

## Examples

- 「このダイアログの文言をレビューして」
- 「設定画面のメニューとボタンのラベルを揃えて」
- 「外部 API がタイムアウトしたときのエラーメッセージを書いて」
- 「UI の用語集を作って」
