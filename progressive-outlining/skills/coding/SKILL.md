# Progressive Outlining: Coding

実装の 1 箇所を直しても 1 関数しか変わらないが、インターフェースの 1 箇所を直すとそれに依存する実装すべてが変わる。
このため往復は構造とインターフェースが固まる前に集中させ、実装はその後に行う。

brief を作る、構造案から 1 つ選ぶ、責務を書く、インターフェースとテストケースまで細かくする、と進む。
brief と案は一続きで書き、最初の止まり所は案の選択。案の採用以降は成果をファイルに書くたびに止まり、ユーザーの返答で次に進む。成果物は設計文書で、この skill では実装を書かない。
どこまで分解してから実装に入るかはタスクで決め、ユーザーはどの時点でも実装に移れる。

## 作業ファイル

往復は設計文書そのもので行う。brief や構造のような長い内容はチャットに貼らず、ファイルに書いてユーザーに読んでもらう。
リポジトリに設計文書の置き場 (`docs/design/`、`docs/adr/` など) があればそこに `<slug>.md`、なければカレントディレクトリに `<slug>.design.md` を置く。slug は題材から Claude が決める。scratchpad は使わない。

```markdown
---
stage: responsibilities   (現在の段階。brief | candidates | responsibilities | interface | done)
---

# Brief        (目的、制約、非目標、既存コードの調査結果)
# Candidates   (構造案。採用後に削除)
# Structure    (採用した構造。コンポーネントごとに見出しを立て、下に責務、インターフェース、テストケースが育つ。層があれば ## を層、### をコンポーネントに)
# Notes        (採らなかった案とその理由、保留した論点、参照したコードや資料)
```

作業ファイルが既にあれば `stage` を読んで続きから始める。ユーザーが設計メモや構造図を持ち込んだら `# Structure` に写し、構造もそのまま使う。
成果を書いたら作業ファイルをエディタで開くよう促す。

## フィードバック記法

長い内容への意見はチャットではなくファイルで受け取る。ユーザーは作業ファイルを直接編集するか、マーカーでコメントを書く。マーカーのない直接編集は確定した変更として扱う。

```markdown
>> ファイル冒頭なら全体へのコメント

## Repository 層
>> 見出し直下ならこのコンポーネント全体へのコメント

- `fetch(id) -> Item`: ID で 1 件取る
>> 直前のブロック (項目とその子) へのコメント

戻り値は {Item>>Optional にして、無ければ None} とする。{キャッシュは持たない>>}   (範囲指定。コメントが空なら削除候補)
```

読み直すときは `>>` を rg で拾い、反映してマーカーを消す。判断が要るものと反映しなかったものはチャットで短く返す。
チャットで受けた指示も反映先はファイルで、直した内容をチャットに書き写さない。

## 進め方

### Brief

**brief** は目的と利用者、満たすべき振る舞い、制約 (言語、フレームワーク、性能、互換性、期限)、非目標、既存コードとの関係をユーザーと合意した文書で、以降の判断の基準になる。
既存リポジトリなら、関係するコード、慣習、依存、テストの書き方を調査し、要点を `# Brief`、詳細を `# Notes` に書く。調査は Explore agent に任せてよい。
引数や会話から分かる項目はそのまま brief に書いて聞き直さない。足りない項目は案を出す前に AskUserQuestion で一度に聞き、聞けない状況なら仮定で埋めて進む。答えられない項目は `# Notes` に保留として書き、brief には置いた仮定を明記する。

### 構造案

分割に選択肢が意味を持つなら、どの変更がどのコンポーネントの中だけで済むかが違う案を 2〜3 つ `# Candidates` に書き、何を優先した分割かを 1 行で添えて AskUserQuestion で選んでもらう。実質 1 つなら 1 案で確認する。
各案に、コンポーネント一覧、依存の向き、brief の主要な要求を満たすコンポーネントを示す。粒度は規模で決め、関数の一覧から層やモジュールまで幅がある。
ユーザーが `# Candidates` に自分の案を書いたらそれを採用し、どれも採用されなければフィードバックを反映して出し直す。採用した案を `# Structure` に移し、`# Candidates` を消す。

### 責務

各コンポーネントに責務を 1 行で書く。何を知っていて、何を決め、何を知らないかが分かる文にする。
1 行で書けないコンポーネントは分割候補、責務が重なる 2 つは統合か境界の見直し。

### インターフェースとテストケース

各コンポーネントに次の層 (インターフェース、次いでテストケース) を足すのが一段で、一段進めるごとに止まる。

- インターフェース: コンポーネント間で合意が必要な契約。ファイル配置とそこに実装するものの一覧で足りることも多い。必要なら公開 API、CLI、イベント、スキーマ、設定を言語の記法で書く
- テストケース: 期待動作を「入力 → 期待結果」の一覧で書く。正常系、境界、エラーを含める。テストコードは書かない
- アルゴリズムや擬似コードは、インターフェースを決めるのに必要な範囲でだけ書く

分解の深さはタスクで決める。既存パターンの繰り返しなら責務まで、新しい境界を作るならインターフェースとテストケースまで。コンポーネントごとに深さが違ってよい。

### 設計を終える

ユーザーが実装に入ると決めた時点で設計を終える。各コンポーネントの責務、最初に手を付けるコンポーネントのインターフェース、依存の向きの説明があれば、残りの判断は実装しながらで足りる。
決めていないことは `# Notes` に「実装時に決める」として残す。`# Candidates` を消して `stage: done` にし、設計文書として読める形に整えて止まる。frontmatter を外すかは置き場の慣習に従う。

## 止まった後の指示

成果をファイルに書いて止まるとき、チャットには何を書いたかと推奨する次の一手を 1〜2 行で返す。構造やインターフェースそのものは貼らない。
AskUserQuestion は brief の不足項目と構造案の選択にだけ使い、次の進め方を聞くのには使わない。ユーザーはファイルを読んでから返答し、その内容で次が決まる。

- マーカーや直接編集を入れて反映を求める: 同じ段階をもう一往復。反映して止まる
- 次へ: 次の段階の成果をファイルに出して止まる
- 残りを自走: 残りの段階を批評役と往復して設計を仕上げ、止まる
- 実装へ引き渡す: ここで設計を終え、設計文書に整えて止まる

責務が確定した後、構造が固まっていて、brief と作業ファイルだけで意図が復元でき (ユーザーだけが知る運用上の事情を足す必要がない)、成果を brief と照らして Claude 自身で検証できるなら自走を、残りの判断が実装しながらで足りるなら実装への引き渡しを、どちらでもなければ「次へ」を推奨する。
マーカーが前の段階の内容に触れていたら、触れている中で最も上流の段階に `stage` を戻して反映し、そこから止まる。

## 自走

ユーザーに確認せず進めること。**批評役**は会話文脈を持たない新規の general-purpose agent で、fork は使わない。渡すのは brief、現在の設計、関連コードのパス、確認してほしい観点だけ。
自走の範囲が終わるまで止まらず、AskUserQuestion も使わない。Agent ツールがない環境では自走を案内しない。

- 批評役には「brief のどの要求を満たすコンポーネントがないか、責務の重複や漏れはどこか、このインターフェースで書けないテストケースは何か、依存に意図しない循環や逆流はないか、既存コードと矛盾する点はどこか」を列挙させる。称賛は求めない
- 指摘を反映し、反映しなかった指摘と理由を `# Notes` に残す
- 一段ごとに批評役と往復し、新しい重大な指摘がなくなったら次の段へ進む。一段あたり数往復が目安
- 判断できない論点は `# Notes` に保留として書いて進み、終わってから何を決めて何を変えたかを短く報告する

## Examples

- `/progressive-outlining:coding CLI に --watch オプションを足して、ファイル変更で再実行する`
  既存コードを調査して brief を作り、監視、デバウンス、再実行をどう分けるかの構造案を出す
- `/progressive-outlining:coding 既存の Exporter に CSV 形式を追加`
  既存パターンの繰り返しなので、責務を書いた時点で実装へ引き渡すことを推奨する
